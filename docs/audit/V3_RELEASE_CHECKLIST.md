# V3 demo and deployment checklist

This checklist prepares a private candidate. Application Production promotion requires the user's explicit approval after acceptance. The separate V1 production and V2 preview remain preserved.

## Before private Preview

- [ ] Keep v1-stable, the V2 recovery reference, the pre-P0 V3 reference and their deployments/data/configuration. Retain the old audit and evidence. Record remediation branch/commit and recovery bundle verification.
- [ ] F01 root/brand/mode labels and F05/F06 regressions pass. The V3 deployment root uses explicit V3 opt-in; flag-off builds retain the existing V1 root behavior.
- [ ] Execute focused regressions, pnpm verify, pnpm test:e2e, pnpm check:audio and pnpm check:v1. Record command, observed result, count/duration when available and logs. Fixtures are labelled; no phone/API success is inferred.
- [ ] Verify candidate build has no mock mode or credential values in browser/source outputs. Use server-only sensitive Preview variables already approved for the dedicated V3 project. Never print keys, admin secrets, proof secrets, store tokens or bypass tokens.
- [ ] Confirm the deployment targets **scamsuno-v3 Preview**, its separate database and V3 credentials; do not link the old V1/V2 projects. No schema reset, data overwrite or paid upgrade.
- [ ] Keep live admission closed unless fresh reconciliation and a bounded test window are explicitly recorded. Balance stays unknown without current provider evidence. Do not reset request accounting or unacknowledged unknown-charge holds.
- [ ] Deploy candidate Preview (not --prod); inspect build/health and `/` → `/v3` language-preserving entry without triggering providers. Record immutable URL/deployment ID/exact commit in V3_REMEDIATION_RESULTS.md. Keep Vercel protection enabled.

## Before participant testing

- [ ] Follow V3_DEVICE_ACCEPTANCE.md preflight. Verify the participant can sign into the private candidate on Android Chrome.
- [ ] Record fresh nonsecret provider balance/usage and local policy/counters. Plan six speech attempts for one exchange each in Tamil and Telugu, with a small bounded model allowance and one active attempt. Do not describe this as a guaranteed credit cost.
- [ ] State the actual expiry in IST. Pause if budget is unknown, exhausted or expired. No automatic renewal.
- [ ] Participant performs real Tamil and Telugu tests and supplies result forms. Record failures honestly. iPhone remains unverified.

## Exact short demo sequence

1. Open the recorded V3 Preview, confirm V3 and educational simulation labels, select the accepted language.
2. Answer and let the fictional opening finish. Show that category is hidden.
3. Speak one original clarification, review the transcript and confirm/send. Explain that recording is turn-based and limited to 15 seconds; no automatic interruption is claimed.
4. Listen to the response. Open the simulated independent-check panel using a channel separate from the caller.
5. End. Show the revealed scenario, supported observations and not-tested dimensions. Explain that the panel corroborates/contradicts a notice, not caller identity.
6. End recording of the demo. Reconcile usage and close live admission. If editing a demo video, disclose cuts and do not splice a fabricated successful conversation.

Keep V1 available through its explicit **V1 fallback · scripted practice** link if the candidate fails. Tell the audience which generation they are seeing; do not present V1 as V3. A fallback is useful recovery, not proof that V3 acceptance passed.

## Before any public application promotion

- [ ] All P0 regression and actual device acceptance results are recorded; no silent provider fallbacks/errors remain unexplained.
- [ ] Exact public entry, judge signed-out access and remaining operational window are tested under approved settings. Private Preview sign-in is not public demo access. Do not disable protection without authorization.
- [ ] Reconcile fresh provider usage; document the shared V1/V3 account limitation, caps and pause operator. Request-count ceilings do not guarantee an account-wide monetary reserve.
- [ ] Back up current source/environment metadata/database and test the planned recovery without erasing later billing evidence. Keep old deployments and references. Rollback must preserve production data and spending holds.
- [ ] Present exact commit/deployment, test summary, phone outcomes and residual risks to the user and obtain explicit production approval. A static bootstrap approval does not authorize application promotion.
- [ ] Only after approval, promote that tested candidate and verify the public V3 journey/access, budget gates, mobile voice and V1 availability. On failure, pause V3, restore the last verified candidate/alias according to the tested plan, preserve data and report the observed issue.
